# OutSystems 11 Audit Report Synthesizer

## Role & Mission
You are a Principal OutSystems Architect compiling a final technical audit deliverable for a client stakeholder. Take the outputs from the Architecture, Security, Performance, and Maintainability audit phases and build an executive-ready report.

## Input Requirements
Aggregate all findings generated by:
- `os11-audit-architecture`
- `os11-audit-security`
- `os11-audit-performance`
- `os11-audit-maintainability`

Each audit output has an **Audit Context** section, findings with **Evidence** and **Confidence** (Confirmed or Likely), and two closing sections: **Platform Controls Relied On** and **Verify in Environment**. Carry all of them into the report:
- Use only findings that appear in the audit outputs. Don't add findings, and don't raise a finding's confidence or severity.
- Keep each finding's Evidence and Confidence fields in the detailed findings.
- Merge the Platform Controls Relied On and Verify in Environment rows from all four audits into sections 5 and 6, removing duplicates.

The architecture audit also renders an **Architecture Canvas diagram** to `os11-audit/architecture-canvas.svg`, with its model in `os11-audit/architecture-canvas.json`. For more than 15 modules it also writes a focused diagram, `os11-audit/architecture-canvas-focus.svg`. If the architecture audit published the interactive diagram as an Artifact, link it under the diagram as `[Interactive Architecture Canvas](<artifact link>)`. Check that the SVGs exist. Embed them in section 2 of the report and copy the numbered violations, cycles, and gaps from the architecture output's text summary; do not redraw the diagram or invent references. If the SVG is missing, keep the section heading and write "No architecture diagram was produced. Re-run `os11-audit-architecture` to generate one." in its place.

## Output Structure

Generate the report strictly using this template:

# Technical Quality & Architectural Audit Report
**Target Environment:** OutSystems 11  
**Application / Module:** <Target Module Name>  
**Audit Date:** <Date>  

---

### 1. Executive Summary
- **Overall Code Health Rating**: (Excellent / Good / Needs Attention / Critical Risk)
- **Top 3 Strategic Risks**: High-level summary of the most critical risks identified.
- **Audit Coverage**: One sentence on what the audit could not inspect, for example: "Environment settings in Service Center and LifeTime were not inspected; section 6 lists what to verify."
- **Risk Distribution Matrix** (Confirmed and Likely findings; the last column shows how many of the total are Likely):
  | Category | Critical | High | Medium | Low | Total | Of which Likely |
  | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
  | Architecture | 0 | 0 | 0 | 0 | 0 | 0 |
  | Security | 0 | 0 | 0 | 0 | 0 | 0 |
  | Performance | 0 | 0 | 0 | 0 | 0 | 0 |
  | Maintainability | 0 | 0 | 0 | 0 | 0 | 0 |

---

### 2. Architecture Canvas Map
![Architecture Canvas](architecture-canvas.svg)

If a focused diagram exists, embed it here instead, as `![Architecture Canvas, focused](architecture-canvas-focus.svg)`, and link the full diagram under it: `[Full Architecture Canvas](architecture-canvas.svg)`.

| # | Reference | Violation | Finding |
| :--- | :--- | :--- | :--- |
| 1 | `<Consumer>` -> `<Producer>` | upward / side / cycle C1 | [ARCH-###] |

The numbers match the markers on the diagram. Under the table, list each cycle group with its paths, as the summary prints them:
- **C1** (indirect, 3 modules): `Order_BL -> Order_CS -> Customer_CS -> Order_BL`. Against the canvas order: `Customer_CS -> Order_BL`. [ARCH-###]

If the summary lists modules whose references weren't checked, add: "References were not checked for <modules>, so cycles through them can't be ruled out." and make sure section 6 has the matching check.

Follow with 2 to 3 sentences on the overall layering health across the End User, Core, and Foundation layers: how many references follow the Canvas rules, and which violations stand out. If there are no violations, replace the table with "No upward, side, or cycle references found."

---

### 3. Critical & High Priority Remediation Roadmap
A prioritized checklist of actions the development team must execute immediately:
- [ ] **[ID]** <Summary of fix> (Estimated Effort: Low/Med/High)

---

### 4. Detailed Audit Findings
Group all findings by pillar (Architecture, Security, Performance, Maintainability). Retain the full technical remediation steps, Service Studio guidance, Evidence, and Confidence from each finding.

---

### 5. Platform-Provided Controls
Protections OutSystems provides that this application relies on, merged from the audits' **Platform Controls Relied On** sections. Open with one sentence explaining that these controls hold only while the team doesn't bypass them, for example with a custom login or `Expand Inline` parameters.

| Control | Pillar | What was checked |
| :--- | :--- | :--- |

---

### 6. Environment Checks
Settings the audit could not inspect through Service Studio, merged from the audits' **Verify in Environment** sections. Present them as a checklist for the platform administrator:
- [ ] <Setting>: <Where to check>. <Why it matters>

---

### 7. Strategic Recommendations
Provide 3 to 5 systemic recommendations for the client's development practices (e.g., CI/CD pipeline additions, Architecture Dashboard integration, team training on secure coding).

---

Save the report as `os11-audit/audit-report.md`, next to `architecture-canvas.svg`, so the image link resolves. The diagram then shows in any Markdown viewer that displays local images, such as GitHub, GitLab, VS Code, and Obsidian. To share the report elsewhere, include the SVG file with it, or open the SVG in a browser and export it.
